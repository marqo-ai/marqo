# Ranking Query
Currently, we only allow for 1 vector to be sent to vespa for a tensor search, which is used for both retrieval and
ranking (or just ranking in the case of a lexical/tensor hybrid search). This feature is to use a different vector 
to rerank all results in the custom searcher (before applying global score 
modifiers).

This is only applicable for hybrid search (searchMethod="HYBRID"). To do this, we will use the rank() feature of 
vespa to obtain the closeness of each retrieved doc to a ranking vector, then use it in the java searcher for reranking.

### API Change

- New search parameters
    - `hybrid_parameters.rankingQueryTensor`of type `Optional[Union[str, dict]] = None`
    - `rankingContext` - of type `SearchContext`

### API Model Changes
- New `SearchQuery` parameters
    - `hybrid_parameters.rankingQueryTensor`of type `Optional[Union[str, dict]] = None`
    - `rankingContext` - of type `SearchContext`

#### Python Search Logic Changes
- The current logic we have to create the marqo query embedding should stay the same, but will now become 
  `marqo__retrieval_query_embedding`. But now we will have a new `marqo__retrieval_query_embedding` which is made by 
  vectorizing `hybridParameters.rankingQueryTensor` interpolated with `rankingContext`, in the same way retrieval 
  vector is created. If neither `hybridParameters.rankingQueryTensor` nor `rankingContext` is provided, then the 
  ranking vector will just be the same as the retrieval vector.

- Optimization - We should fetch documents in `hybridParameters.rankingContext.documents.ids` and `context.documents.
ids` at the same time so there's only 1 request.

- yql queries
  - If a ranking vector is defined, the yql query should be:
    - For lexical search - `rank(lexical_term, ranking tensor terms)`
    - For tensor search term - `rank((retrieval tensor terms ORed together), ranking tensor terms)`. We will have to 
      split the retrieval and ranking terms. 
  - If there's no ranking vector, use the original yql queries.
  - ranking tensor terms - for each term generated by `_get_tensor_search_term`, we must have 2 nearestNeighbor 
    searches, one for retrieval_vector and one for ranking_vector. They should each have a label. Example:
  ```
  select * from index where rank(
    (
        {label:'retrieval_tensor_field1', targetHits:100} nearestNeighbor(marqo__embeddings_tensor_field1, 
  marqo__retrieval_query_embedding) or
        {label:'retrieval_tensor_field2', targetHits:100} nearestNeighbor(marqo__embeddings_tensor_field2, 
  marqo__retrieval_query_embedding)
    ),
    {label:'ranking_tensor_field1'} nearestNeighbor(marqo__embeddings_tensor_field1, marqo__ranking_query_embedding),
    {label:'ranking_tensor_field2'} nearestNeighbor(marqo__embeddings_tensor_field2, marqo__ranking_query_embedding)
  )
  ```

- Update match_features of all relevant rank profiles to have `closeness(label, ranking_tensor_field1)` and

  in the custom searcher 
- `embedding_score()` to use label (for retrieval) instead of field ??

Small example with tensor retrieval and ranking:
```vespa
rank-profile tensor_with_ranking_features inherits base_rank_profile {
    first-phase {
        expression: max(
            if (query(marqo__embeddings_tensor_field1) > 0, closeness(label, retrieval_field1), 0),
            if (query(marqo__embeddings_tensor_field2) > 0, closeness(label, retrieval_field2), 0)
        )
    }
    match-features inherits base_rank_profile {
        # Retrieval closeness (for debugging)
        closeness(label, retrieval_tensor_field1)
        closeness(label, retrieval_tensor_field2)
        
        # Ranking closeness (primary reranking signals)
        closeness(label, ranking_tensor_field1)
        closeness(label, ranking_tensor_field2)
        
        # Ranking distance (for debugging/analysis)
        distance(label, ranking_tensor_field1)
        distance(label, ranking_tensor_field2)
        
        # Existing features for backward compatibility
        closest(marqo__embeddings_tensor_field1)
        closest(marqo__embeddings_tensor_field2)
    }
}
```

#### Java Custom Searcher Changes
- In the hybrid searcher, after fusion but before global score modifiers, rerank fused results by `closeness` to the 
`marqo__ranking_query_embedding`.

SCORES:
In hybrid search, every doc should have the following scores:

- `_tensor_score` - raw tensor score, if present
- `_lexical_score` - raw lexical score, if present
- `_pre_rerank_score` (NEW) - Combined RRF score will be saved here (or just normal score after lexical/tensor, 
  tensor/lexical, etc), so it is not lost when reranking is done on the ranking tensor.
- `_score`
    - If ranking tensor is present, his will now be the reranked tensor score with the ranking tensor.
    - If not, `_score` will just be the old RRF score.
